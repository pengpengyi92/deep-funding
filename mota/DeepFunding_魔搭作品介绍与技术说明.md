## 摘要

融资不是一次简单的信息搜索，而是企业与资金方在发展阶段、行业方向、融资金额、地域、风险偏好、资源能力和时间窗口上的双向选择。

DeepFunding 是一个面向创业者、企业及资金方的开源 Agent-to-Agent（A2A）融资匹配平台。创业者或企业拥有自己的 Company Agent，VC、PE、银行、天使投资人、孵化器及产业基金等资金方拥有 Funding Agent。系统通过结构化建档、硬约束过滤、语义匹配、可解释评分和反馈闭环，帮助双方在正式会面之前完成高成本、重复性的初步筛选。

DeepFunding 当前以可公开体验的 MVP 为核心：用户可选择企业端或资金端身份，填写关键资料或加载匿名演示案例，获得 Top-K 候选、分项匹配得分、匹配理由、潜在缺口、风险提示与下一步行动建议。项目采用 Python、FastAPI、SQLAlchemy 与 SQLite 构建轻量后端，并为后续 PostgreSQL、向量检索、主体 Agent 注册、权限控制、订阅/API 服务及尽调协作预留接口。

DeepFunding 的目标不是替人作出投资或融资决策，而是把零散、不可复用的前期沟通转化为结构化、可解释、可评测和可持续改进的开放基础设施。

## 一、项目背景：融资匹配为什么需要 Agent

### 1. 企业端的痛点

同一家企业面对不同资金方，往往需要反复整理相似材料；但不同资金类型的关注点并不相同：

- 天使投资人和孵化器更关注创始团队、技术能力、产品原型与早期验证；
- VC 更关注市场空间、产品、增长、客户、商业模式和可扩展性；
- PE、银行及产业基金通常需要更成熟的收入、利润、现金流、资产负债、合同、治理与合规证据。

企业如果没有先判断自身阶段和材料完备度，容易找错资金类型、提交不完整信息，或在低适配对象上消耗大量时间。

### 2. 资金端的痛点

资金方需要面对大量格式不统一、证据质量不一致的项目资料，并在有限时间内判断：项目是否符合投资阶段、行业范围、地域限制、票面区间、成熟度要求和风险偏好。单纯依赖关键词搜索或静态机构名录，既不能有效过滤硬性冲突，也很难解释“为什么匹配”。

### 3. DeepFunding 的产品判断

DeepFunding 将融资前置流程建模为双边 Agent 协作：

```text
企业资料 → Company Agent ─┐
                           ├→ A2A Match Layer → 可解释候选 → 人类会面/尽调
资金偏好 → Funding Agent ─┘
```

Agent 先完成资料整理、适配分析、证据审计和候选匹配；当双方具有较高适配度时，人类再进入引荐、会面、材料补充、尽调和谈判环节。这样可以把人的精力集中在真正值得推进的关系上。

## 二、产品方案：一次完整匹配如何发生

### 步骤 1：双边结构化建档

企业端填写或导入行业、阶段、产品、团队、融资金额、资金用途、地域、收入/增长、客户、核心优势、关键风险及资源需求。资金端填写机构类型、投资阶段、票面范围、行业偏好、地域、禁投项、成熟度要求与可提供的增值资源。

系统同时保留三类信息状态：用户提供、外部验证、Agent 推断；缺失或未经验证的内容不会被包装成确定事实。

### 步骤 2：Information、Analysis、Audit、Match 协作

DeepFunding 在企业端和资金端均采用可组合的职能划分：

| Agent | 主要职责 | 典型输出 |
|---|---|---|
| Information Agent | 收集、清洗并标准化主体资料 | 结构化 Profile、缺失字段 |
| Analysis Agent | 分析成熟度、融资准备度与偏好 | 适合/不适合的资金类型、优势与风险 |
| Audit Agent | 检查完整性、一致性、证据与推断边界 | 审计状态、警告、置信度 |
| Match Agent | 执行双向筛选、排序和解释 | Top-K 候选、分项得分、匹配理由 |

当前 MVP 将这些职责落在共享服务层中，以保证单元可测试；未来可将其扩展为可注册、可协商的独立 Agent。

### 步骤 3：硬约束优先过滤

第一阶段由确定性程序处理不可妥协的条件，例如：

- 融资金额是否落入资金方票面范围；
- 企业阶段是否属于资金方覆盖阶段；
- 地域是否满足要求；
- 是否命中禁投行业或其他排除项；
- 必要资料或成熟度门槛是否满足。

硬约束不交给模型自由判断，从而避免出现“解释听起来合理、实际上无法执行”的推荐。项目的底线评测目标是硬约束违反率为 0。

### 步骤 4：多维评分与语义排序

通过硬约束的候选进入第二阶段排序。MVP 使用可配置权重计算综合分数：

```text
Score = 0.25 × StageFit
      + 0.20 × TicketFit
      + 0.20 × SectorFit
      + 0.15 × GeographyFit
      + 0.10 × ResourceFit
      + 0.10 × SemanticFit
```

其中阶段、金额、行业、地域和资源适配主要来自结构化字段；模型用于理解项目描述、投资逻辑和资源诉求等非结构化内容，并辅助生成清晰解释。权重存放于配置层，不写死在提示词中，因此结果可复现、可调优、可做版本对比。

### 步骤 5：输出可解释报告

系统不仅给出总分，还回答：

- 哪些维度形成了匹配；
- 哪些条件仍存在差距；
- 哪些资料需要补充或验证；
- 有哪些潜在风险；
- 下一步适合请求引荐、补材料，还是暂缓接触。

用户可以进一步执行 `Request Introduction`，把高适配候选从机器筛选推进到人类沟通。

### 步骤 6：反馈闭环

收藏、忽略、联系、请求引荐、进入尽调等行为会形成反馈事件。后续可用这些反馈校准权重、构建 Benchmark，并比较不同规则或模型版本的表现。

## 三、技术架构与工程实现

### 1. 分层架构

| 层级 | 主要组件 | 设计目标 |
|---|---|---|
| 交互层 | 魔搭创空间 Web 应用、企业端/资金端表单、候选卡片、匹配报告 | 降低体验门槛 |
| Agent/领域层 | Information、Analysis、Audit、Match；Company/Funding 双边领域模型 | 职责解耦、便于测试 |
| 应用服务层 | Profile 服务、匹配服务、报告生成、反馈与审计日志 | GUI、TUI、CLI/API 复用同一业务逻辑 |
| 数据层 | SQLAlchemy + SQLite；主体、偏好、运行结果与反馈事件 | MVP 轻量部署、模式可迁移 |

### 2. 技术选型

- 后端语言：Python；
- API 框架：FastAPI；
- ORM：SQLAlchemy；
- MVP 数据库：SQLite；
- 后续演进：PostgreSQL + pgvector；
- 对外形态：Web GUI、REST API，并为 TUI、CLI 与 JSON 模式保留共享服务接口。

选择 SQLite 是为了让开源 MVP 可以零配置启动、便于本地演示和自动化测试。当主体规模、并发和语义检索需求增长后，数据模型可迁移到 PostgreSQL，并通过向量扩展支持更丰富的相似度搜索。

### 3. 核心数据表

| 数据表 | 用途 |
|---|---|
| `companies` | 企业主体、团队、产品、经营与融资需求 |
| `funders` | 资金方主体、类型、阶段、行业和票面范围 |
| `preferences` | 双方的筛选偏好、资源需求和排除条件 |
| `match_runs` | 每次匹配的输入快照、配置与版本 |
| `match_results` | 候选、分项得分、理由、缺口和置信度 |
| `feedback_events` | 收藏、忽略、联系、引荐、尽调等反馈 |

匹配运行和匹配结果分开存储，使系统能够追溯“当时使用了什么输入、规则和权重”，为后续审计与回归测试提供基础。

### 4. API 设计示例

```http
POST /profiles
POST /matches
GET  /matches/{id}
POST /feedback
```

`POST /profiles` 创建或更新授权主体资料；`POST /matches` 发起一次可版本化的匹配运行；`GET /matches/{id}` 返回候选和解释；`POST /feedback` 写入结果反馈。未来主体 Agent 注册后，可在权限控制下通过同一服务层调用数据和匹配能力。

### 5. 安全、隐私与边界

DeepFunding 默认遵循以下原则：

- 最小必要采集与字段分级；
- 私有融资历史、机构组合和企业材料默认保留在本地；
- 公开仓库只包含 Schema、引擎、测试和虚构/匿名样例；
- 远程模型与外部 API 调用必须显式配置；
- 公开演示不放置真实敏感数据或密钥；
- 清楚区分用户声明、可验证证据和 Agent 推断；
- 系统仅辅助筛选和信息组织，不承诺融资结果，也不构成投资、信贷或法律建议。

## 四、魔搭创空间实践

DeepFunding 通过魔搭创空间提供公开体验，使评委和社区用户无需配置本地环境即可运行核心流程。建议的体验路径如下：

1. 选择“我是创业者/企业”或“我是资金方”；
2. 填写关键字段，或一键载入虚构演示案例；
3. 点击“开始匹配”，查看 Top-K 候选和分项得分；
4. 打开候选详情，查看匹配理由、缺口、风险和下一步建议；
5. 提交“有帮助/不相关”等反馈，观察闭环事件如何沉淀。

部署包包含应用入口、依赖声明、示例数据和使用说明；服务通过环境变量读取运行配置。正式提交前，将使用无痕窗口从零跑通公开路径，确保项目无需内部权限即可体验。

## 五、评测设计：如何证明系统不只是“会讲故事”

DeepFunding 将评测分为确定性约束、排序效果、解释质量、稳定性、安全性和工程性能六类。

| 评测维度 | 指标/方法 | 目标 |
|---|---|---|
| 硬约束 | Constraint Violation Rate | 必须为 0 |
| 排序效果 | Precision@K、Recall@K、NDCG@K | 优于规则或纯语义单一基线 |
| 解释质量 | 具体性、证据一致性、风险充分性、行动可执行性 | 人工标注与抽检 |
| 稳定性 | 同一输入重复运行的候选与核心理由一致性 | 可复现、可回归 |
| 安全性 | 敏感信息泄漏、提示注入、不当承诺测试 | 阻断或明确降级 |
| 工程性能 | 响应时延、失败率、推理成本 | 满足公开演示体验 |

每次规则、权重或模型升级都应在固定样例集上运行回归测试，并保留配置版本。基线实验将比较：纯规则方案、纯语义方案和“硬约束 + 结构化评分 + 语义解释”的混合方案。

## 六、项目创新点与开源价值

### 1. 从静态名录升级为 A2A 工作流

DeepFunding 不只是展示“有哪些机构”，而是让双方的 Agent 读取授权资料、表达偏好、检查证据、执行双向匹配，并把高质量候选推进到引荐或尽调。

### 2. 规则与模型分工明确

金额、阶段、地域和禁投项由确定性规则控制；模型专注非结构化理解与解释。这个组合兼顾语义能力与工程可靠性。

### 3. 匹配过程可解释、可审计

系统保存分项得分、原因、缺口、置信度、输入快照和配置版本，不只输出一个缺乏依据的综合分。

### 4. 双向 Benchmark，而非单边推荐

后续 Founder RSI 将帮助创业者结合自身历史接触记录形成个性化资金方排序；Funding RSI 将帮助资金方把新项目与自己的历史组合、行业或阶段 Cohort 比较。框架开放，但私有数据保持私有。

### 5. 面向社区扩展

社区可以贡献新的资金类型、行业字段、地区规则、数据校验器、匹配器、Benchmark Cohort 和测试集。统一的 Schema、服务接口与评测规则使这些贡献可以被复用，而非沉淀为孤立脚本。

## 七、迭代路线

### V0：可体验 MVP（本次参评重点）

- 双边建档；
- SQLite 数据保存；
- 硬约束过滤；
- Top-K 多维匹配；
- 可解释报告；
- 反馈事件记录；
- 魔搭创空间公开演示。

### V0.2：RSI 与 Benchmark

- Founder RSI 与 Funding RSI；
- 递归、可配置 Benchmark Engine；
- 深圳 VC/PE/孵化器等资金方知识库 Schema 与校验流程；
- BP、财务模型、公司及交易结构、尽调要求的结构化 Benchmark；
- TUI、CLI 与 `--json` Agent 调用模式；
- 隐私优先的本地历史数据分析。

### V1：数据与评测

- 引入经过授权和来源验证的数据；
- 固定 Benchmark 与标注样例；
- 反馈回流、版本化评测和持续校准；
- 从深圳扩展至大湾区、香港及其他市场。

### V2：完整 Agent-to-Agent 协作

- 主体 Agent 注册与身份权限；
- Agent 协商协议；
- 订阅与 API 服务；
- 自动材料请求与 Request Introduction 工作流。

### V3：尽调与融资执行协同

- 材料清单与数据室；
- KYC、合规和证据检查；
- 尽调任务编排；
- 从匹配到融资决策的完整审计链。

## 八、结语

DeepFunding 希望把依赖人脉、零散搜索和重复填表的融资前置流程，转化为结构化、可解释、可评测并能持续改进的 Agent 原生基础设施。

对企业而言，它帮助团队更早理解“我们适合什么资金、还缺什么证据、应该优先联系谁”；对资金方而言，它帮助机构在大量项目中更快识别阶段、行业、金额与资源真正适配的候选；对开源社区而言，它提供了一套可以共同演进的数据模式、匹配接口、Agent 职责和评测框架。

资本与企业最终仍由人作出决定，但在那之前，可以先让 Agent 更高质量地相遇。
