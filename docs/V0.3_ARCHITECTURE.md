# V0.3 Architecture and Boundaries

## Two runtimes, explicit ownership

The existing React/Cloudflare Worker/D1 sandbox stays intact, including the
V0.2 CLI/TUI/browser RSI services. V0.3 adds a separate Python 3.11+ FastAPI /
SQLAlchemy 2 / SQLite single-owner workspace.

| Surface | Runtime | Stored data |
| --- | --- | --- |
| Public knowledge explorers | Worker or local Python | Checked-in public notes only |
| Existing fictional A2A demo | Worker / D1 | Expiring anonymous workspace |
| RSI | Browser memory / local CLI store | User-supplied local files |
| Private profile forms and data explorer | Local FastAPI / SQLite | Local company, provider, need, match and audit records |

**Cloudflare does not run the Python SQLite database.** The public database
page links to a local service without silently querying localhost or uploading
private records. A public hosted account system requires authentication,
tenant isolation, backups, retention and infrastructure work first.

Local default: http://127.0.0.1:8793/data-explorer. The service binds loopback,
rejects untrusted Host/client/Origin, blocks cross-site reads and requires
JSON plus X-Deep-Funding-Local: 1 on mutations. No wildcard CORS. Trusted local
processes can access it: this is not multi-user authentication. Do not tunnel it.

## Persistence

Twelve SQLAlchemy models cover users, founders, companies, funding needs,
providers, preferences, matches, Agent runs, audits, subscriptions, funding
knowledge and compliance cases. Financial inputs are nullable; null is not zero.
Currency is explicit. No implicit currency conversion occurs.

The database URL is configurable for a future database service, but only
SQLite is verified in this release. Schema creation is idempotent for this
initial backend schema, not a production migration framework. Existing D1
tables are neither migrated nor replaced.

Transactions commit before returning success. A real subprocess restart test
proved that company, match and four Agent-run records survive termination.
Match snapshots include input hashes, corpus content hashes and source links;
later company/provider/preference/need changes flag an old match as stale.
Human status updates append audit records and perform no external actions.

## Knowledge graph baseline

Canonical Markdown/YAML trees: funding-rag-graph and compliance-rag-graph.
Metadata, related_ids, categories and source URLs form explicit graph edges.
The initial retrieval baseline is metadata plus keyword lookup, not vector
RAG, a learned ranker or a graph database. No source file is executed.

scripts/build_knowledge.py validates records and emits data/knowledge-public.json.
It reads only those two public trees, never SQLite. CI rejects index drift.
The local backend synchronizes public note snapshots into its knowledge tables
at startup; it does not fabricate private investor mandates from the notes.
Edit knowledge through reviewed repository commits, then rebuild/restart.

Eighteen sourced institutional/program records cover four Shenzhen VC
references, two PE/growth references, three banks, two incubators, HAX, government/
industrial and angel systems, a strategic investor, a subsidy and a university
project. Verification is limited to the cited source scope. Historical material
does not prove current availability. Unverified stage/ticket/application fields
remain unknown. Family office and other incomplete categories have templates.

## Matching and compliance

Information reads persisted profiles and Funding RAG. Analysis compares stated
stage/sector/geography and available threshold data. Audit retrieves relevant
Compliance RAG context and reports missing evidence. Match stores the result.
All four roles are deterministic rules-v0.3.0, with zero runtime LLM calls.
They are auditable service stages, not independently hosted autonomous agents.

The screening score averages only evaluated dimensions; coverage is returned.
Unmeasured founder/team/risk quality stays null. Financial thresholds use annual
revenue in the provider's currency. Preference weights are stored but are not
applied until an appropriate calibrated score exists. Open JSON policies need
human interpretation and are explicitly flagged. No score is a funding probability.
The complete V0.2 weighted/bilateral engine is still available in its own sandbox.

All generated matches need review. Known incompatibilities veto the screening
score; missing data is never treated as approval. Bank/venture-debt cases request
repayment and financial evidence. Collateral is product-specific, not universal.

Named compliance cases require explicit review-topic relevance. Templates ask
for evidence. Neither a media allegation nor a related company case proves
misconduct. Xiaohongshu stays disputed with its reported company response.
The SEC example distinguishes publication of charges from underlying allegations.
No association-based penalty or automatic investment/legal conclusion occurs.

## Limits and next gates

- Hosted private identity, multi-tenant isolation and cross-device private sync: not implemented.
- SQLite production migration/backup automation: not implemented. Back up the closed local DB securely.
- Real investment outcomes, retrieval precision, credit risk calibration: UNMEASURED.
- Subscription is metadata only; billing, quotas and entitlement enforcement are not implemented.
- No real outreach, fundraising, investment transaction or autonomous agent spending.
- V0.2 private stores are not auto-imported into V0.3; use explicit reviewed schema mapping later.
